# Plan to Minimize Vercel Limits Usage

## Current Usage Analysis
Based on the provided usage data and user responses, you're hitting several Vercel limits significantly:

### High Usage Areas:
- **Edge Requests**: 153K / 1M (15% of limit)
- **Function Invocations**: 147K / 1M (15% of limit) 
- **Function Duration**: 20.0 GB-Hrs / 100 GB-Hrs (20% of limit)
- **Fast Data Transfer**: 1.78 GB / 100 GB (2% of limit)

### User Context:
- **90%+ backend API usage** - Limits are primarily from API calls, not frontend assets
- **Heavy searchers** - Users perform many searches and filtering operations
- **All endpoints similar usage** - No single endpoint is the main culprit
- **Basic frontend caching** - Some caching but likely not aggressive enough
- **Active Redis** - Redis is connected and working but cache hit rate unknown
- **No detailed analytics** - Limited visibility into request patterns

## Root Cause Assessment
The API is a Node.js/Express app on Vercel serving name data from MongoDB with Redis caching. Key issues:

1. **High API Call Volume**: 147K function invocations suggests frequent API requests from heavy search/filter usage
2. **Function Duration Issues**: 20 GB-Hrs indicates slow database queries or inefficient processing
3. **Edge Requests**: High edge request count from API calls that could be cached
4. **No Analytics**: Lack of monitoring makes optimization difficult

## Optimization Strategy

### Phase 1: Aggressive Caching Implementation (High Impact)
**Goal**: Reduce API calls by 60-80% through comprehensive caching

1. **Implement Redis Cache-Aside Pattern for All Endpoints**
   - Cache results from `/api/v1/names/:religion` with filters
   - Cache `/api/v1/names/search` results
   - Cache `/api/v1/names/:religion/filters` (long TTL)
   - Cache individual name lookups `/api/v1/names/:religion/:slug`

2. **Vercel Edge Caching Headers**
   - Add `Cache-Control` headers for API responses
   - Use appropriate TTL based on data volatility (filters: 1hr, search results: 5min, individual names: 30min)

3. **Smart Cache Invalidation**
   - Clear cache on data updates (though user says data doesn't change often)
   - Implement cache warming for popular queries

### Phase 2: Database Query Optimization (Medium-High Impact)
**Goal**: Reduce function duration by 40-60%

1. **Add Database Indexes**
   - Index on `name` (for search and sorting)
   - Index on `religion` + `name` (for filtered queries)
   - Index on `origin`, `gender`, `category` fields
   - Compound indexes for common filter combinations

2. **Query Optimization**
   - Optimize aggregation pipelines in `getFilters`
   - Add query timeouts and limits
   - Pre-compute expensive operations

3. **Connection Pooling**
   - Optimize MongoDB connection settings
   - Implement connection reuse

### Phase 3: Request Optimization (Medium Impact)
**Goal**: Reduce redundant requests and improve efficiency

1. **Rate Limiting & Request Deduplication**
   - Implement smart rate limiting based on user behavior
   - Add request deduplication for identical queries
   - Use Vercel Edge Middleware for pre-processing

2. **API Response Optimization**
   - Implement response compression
   - Add pagination limits and validation
   - Optimize JSON serialization

3. **Frontend Integration**
   - Enhance frontend caching to reduce API calls
   - Implement request batching where possible
   - Add offline capabilities

## Technical Implementation Details

### Caching Strategy
- **Filters endpoint**: Cache for 1 hour (data changes infrequently)
- **Search results**: Cache for 10 minutes with smart invalidation
- **Paginated lists**: Cache for 15 minutes with parameter-based keys
- **Individual names**: Cache for 30 minutes

### Cache Key Strategy
- Include all relevant parameters (religion, filters, pagination, search)
- Use consistent key format: `names:{religion}:{filters}:{page}:{limit}`
- Hash complex filter objects for cache keys

### Monitoring Requirements
- Add cache hit/miss counters
- Log slow queries (>500ms)
- Track request patterns by endpoint
- Implement basic analytics endpoint

This plan preserves API output while dramatically reducing Vercel usage through intelligent caching and optimization.
